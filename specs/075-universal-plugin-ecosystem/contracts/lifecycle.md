# Lifecycle
Publisher release draft -> submitted -> approved -> published -> revoked (terminal; supersede with new version). Reject/rework returns to draft with new immutable submission digest. Install requested -> resolving -> installed -> active -> disabled/suspended -> uninstalled. Upgrade validates graph/signature and stages migrations then atomically switches pointer; failed switch retains old usable release, rollback only to trusted compatible nonrevoked digest. Revocation cancels sessions/jobs and removes access; bounded offline lease revalidation on reconnect. Entitlement expiry disables paid invocation not authorized data/export. Lock graph deterministic, semver and host range negotiated, cycles rejected. Audit every transition with actor/revision; install/uninstall idempotent; no destructive data deletion implicit.

### Wave 0 Web preview refinement
A signed v2 contribution can declare optional nonempty dependencies as {key,range}. Omit the field for no dependencies (preserves legacy envelope signing bytes). The preview resolves only already-active reviewed dependencies; the manager sees exact versions, then submits lock_digest and grant_revision. The approval binds canonical activation revisions and manifest IDs as well as signed release digests. Every execution checks the current lock and project-wide maximum previously approved epoch. Existing approvals lacking a lock require reapproval. This is not automatic multi-package install or rollback.
Catalog v2 now requires operator catalog_signature over canonical {schema:"openvietgis.marketplace.membership.v2",epoch,members:[{envelope_digest,publisher_signature,operator_signature},...]}; order is signed. Regenerate unsigned v2 snapshots, never reuse an epoch for changed membership. The signing CLI review creates a one-release catalog; assemble PRIVATE_KEY EPOCH OUTPUT CATALOG... merges operator-signed same-epoch catalogs. Omitting all inputs creates a signed empty catalog. Operator keys are not shared with plugins. Catalog withdrawal denies runtime access; project epoch floor applies to previously approved epochs only. A global durable watermark and key-rotation distribution are separate open requirements.

### Transactional graph preview/install/switch (Wave 0 candidate)
Organization owner/admin reviews a deterministic signed graph at POST /organizations/{organization_id}/marketplace/v2/graph/preview and submits the exact plan_digest and a request UUID to /install. Register every manifest in dependency order in one existing OrgExtensionScope transaction. Identical already-installed manifests may be reused; conflicting bytes, disabled manifests, stale catalog epochs and request-ID conflicts fail closed. A graph receipt is append-only. Registration does not activate a project.
Project manager independently previews /organizations/{organization_id}/projects/{project_id}/extensions/v2-graph/preview and submits the exact plan_digest, expected activation pins and request UUID to /apply. All selected manifests must already be registered. One project transaction applies compatible changes, appends existing canonical activation/audit events and a graph receipt. Unchanged active pins are not modified. Transition or deactivation advances canonical revision, invalidating earlier v2 grants. No new grants are issued; a graph operation does not remove a grant on an unchanged pin.
Preview currently restricts to reviewed Web 1.0.0 stateless partner contributions, zero assets, read-only command schema. Forward transitions are same-major and preserve data contract and capabilities. A rollback selects the exact prior graph by recorded request UUID, requiring current activation pins equal recorded after state, all prior pins active, same graph keys, still-reviewed target releases, and compatible contracts. No rollback of fresh installs, arbitrary downgrade, graph-shape/data migration, automatic removal of dependencies or native install. Old data remains intact. Outside-graph activation records are not changed; their v2 execution lock may fail closed until reapproval if a shared dependency changes.
Both operations are separately authorized and atomic within their own transaction, not a distributed atomic transaction across organization registration and project activation. Retries require the current catalog to still resolve the same plan; receipts are historical. Feature gate remains off by default. Migration 0056 adds immutable org/project receipt tables; forced RLS and actor binding; no parallel registry. Full integration qualification pending.
