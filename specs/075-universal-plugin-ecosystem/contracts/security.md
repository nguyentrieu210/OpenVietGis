# Threat model and release controls
Threats: malicious publisher/assets, dependency confusion, downgrade/replay, cross-tenant IDOR, prompt injection, SSRF, zip bomb, denial-of-service, secret exfiltration, offline revocation and webhook forgery. Default deny, verified publisher/operator signatures + digests + revocation epoch, namespace allowlist, dependency lock, safe extraction, quota and bounded parser, isolated process/WASM only after review, no arbitrary outbound network or credentials, no direct DB. Per-resource auth and RLS; audit separate from logs; no secrets or raw PII in telemetry. Explicit human approval for irreversible AI actions, publication and sensitive capture; privacy retention/consent. Supply chain pinned versions/SBOM/license scan, critical/high vulnerabilities block release. Test tamper, stale epoch, replay, permission revocation, worker termination and data export. SCADA read-only; engineering/survey outputs not legal or safety certification.

### Global V2 trust checkpoint and key generations
A configured V2 catalog now requires a separately pinned offline trust authority public key (OPENVIETGIS_MARKETPLACE_TRUST_ROOT_PUBLIC_KEY) and signed policy path (OPENVIETGIS_MARKETPLACE_TRUST_POLICY_PATH). The root is distinct from the operator and catalog publishers. The policy schema openvietgis.trust.policy.v1 binds sequence, catalog_epoch, catalog_membership_digest, operator_key_id (SHA-256 of raw public key), issued_at, expires_at and sorted cumulative revoked_release_digests, revoked_publisher_keys and revoked_operator_keys. Maximum validity 30 days; each revocation list max 4096 entries. Signature is Ed25519 over canonical policy JSON. The catalog membership digest is the SHA-256 of the canonical membership signature payload, not a file hash.
All V2 catalog loads used by marketplace, runtime, grant, graph and sandbox-order creation verify the policy and catalog and admit the checkpoint using the global PostgreSQL transaction lock. Migration 0059 persists append-only accepted sequence and policy; reject lower sequence/epoch, equivocation at the same sequence or epoch, removed revocations, changed trust root and unauthorized operator rotation. An operator rotation requires a new catalog epoch and revocation of the old operator fingerprint in the new root-signed policy; re-sign both v1/v2 catalogs with the new operator. V2 release/key revocations are filtered before access. No DB or no valid policy means fail closed for configured V2; default no-catalog disabled state remains available. The trust checkpoint is installation-global across API instances sharing this DB, not global across separate deployments. Admission precedes execution: already admitted in-flight requests and previously confirmed Core jobs are not retroactively cancelled. Policy and catalog files must be deployed together by the operator; checkpoint activation occurs when a verified request admits the new policy. V1 endpoints do not consult this V2 denylist.
Offline signing: trust_policy_sign.py ROOT_PRIVATE OPERATOR_PUBLIC CATALOG REVOCATIONS SEQUENCE ISSUED EXPIRES OUTPUT [--previous PREVIOUS_POLICY]. Use separate private keys offline; revocations JSON contains the three arrays above. Tool checks operator membership/review signatures and monotonic predecessor; runtime also checks publisher signatures for compatible entries. No signing authority in API or browser. Back up trust checkpoints; restoring a stale DB alone cannot guarantee anti-rollback. Root-key replacement and disaster recovery require a separate audited recovery procedure.
Migration 0060 snapshots historical publisher signing public keys on v1 submission rows (backfill plus insert trigger), adds current key_revision and append-only rotation evidence. Publisher self-service rotation requires signatures from both old and new keys binding user_id, publisher_id, expected_revision and both public keys; uses existing human session, CSRF, owner advisory lock and revision CAS; denies historical-key reuse. Developer console and publisher_rotate.py generate/submit proof without uploading private keys. Old submissions remain verifiable with their original key. A registration key rotation does not itself withdraw old releases from catalog; operator must sign a root policy revoking the compromised key, remove or reissue releases and publish the appropriate catalog. Legacy V1 catalog supports one key per publisher: do not combine old/new signed versions under the same publisher in one V1 snapshot without a new versioned trust contract. Lost-key recovery not implemented.

### Verified catalog snapshot cache
One snapshot per AppState shares verified V1/V2 releases, parsed policy, and normalized search text across all host profiles. Cold verification validates every member before host filtering. The single-flight async guard remains owned by the blocking verifier if the caller is cancelled. On Unix, cache identity includes the configured paths, epoch, operator/root key and each local file's device, inode, length, mtime and ctime; files must be regular and stamps must match before and after verification. Non-Unix bypasses this cache. This is a trusted operator-owned local-filesystem contract, not a mechanism to detect hostile filesystem/OS manipulation. Publish catalog and policy atomically; failures, missing files and expiry fail closed. No stale fallback. Every admission, including warm hits, checks the policy validity window and the existing durable PostgreSQL trust checkpoint. An already admitted request can finish after a concurrent update, as before. No trust-policy state is cached in lieu of the DB checkpoint.
