# Command broker
Proposed logical request: command_id, release_digest, project_id, resource_ids, typed input, expected_revision, idempotency_key. Actor/org come from authenticated server context, not trusted body. Validate active installation, signature/revocation, capability, current grant, resource ownership, schema, consent class and quota before dispatch. Async jobs carry scoped service grant and recheck at execution/output. Response: operation_id, status, typed output or job_id, revision, provenance, audit_ref. Errors stable: INVALID_INPUT, UNAUTHORIZED (401), FORBIDDEN (403), NOT_FOUND (404 without resource leak), CONFLICT (409), INCOMPATIBLE (422), QUOTA (429), UNAVAILABLE (503). Idempotent retries return recorded receipt, mismatched payload conflicts. Cancel and unsubscribe on scope switch/revoke. No raw SQL, arbitrary network, tokens or device handles exposed. Read-only vs mutation vs publish explicitly distinguished.

### Processing proposal preview (Web 1.0.0)
The signed declarative action gis_processing_plan uses a distinct explicit ext.<key>.processing_plan permission, derivable only from a reviewed legacy map_view capability. Existing map_view-only releases cannot invoke it. Its single required text field request contains a JSON object with algorithm_id, input_layer_id, optional overlay_layer_id, parameters and output_name. The server uses the canonical Core registry (Buffer, Clip, Dissolve, Difference, Intersection, Union, Reproject, Spatial Join) to normalize parameters, resolves ready sources within the authorized project and returns immutable source revision pins. No raw SQL, geometry, attributes, network calls or arbitrary executable commands.
Preview produces a stored proposal bound to the invocation receipt, human actor, manifest and activation revision, signed release, dependency lock, grant revision, epoch and plan digest. It expires after five minutes. The trusted Web host displays the normalized plan separately and submits POST /organizations/{organization_id}/projects/{project_id}/extensions/{manifest_id}/v2-runtime/processing/confirm with proposal_id and plan_digest only after an explicit host confirmation. This is not an action in the declarative plugin document. The server requires a human manager and CSRF, rechecks current grant and release/dependency binding, exact normalized plan and live source pins, then creates the canonical queued job and unique approval receipt in one transaction. Retries within the validity window return the existing job. Limit 5000 features per source at preview, 10 queued/running jobs per project at approval, existing invocation semaphore/quota and Core execution resource bounds. Existing Core processing workbench is responsible for manual start/retry and cancellation with its ordinary ACL and pinned-source checks. Approval transfers control of the queued job to Core; later plugin grant revocation does not cancel an already approved Core job. No direct plugin execution, automatic background worker, geometry mutation broker or native processing UI is enabled by this preview.

### Invocation binding and audit export
The V2 invocation request now requires grant_revision (decimal string), lock_digest and catalog_epoch in addition to release_digest, activation_revision, action_id, request_id and input. The server compares the client snapshot with current authorization, and binds these values into the invocation fingerprint. Older invocation requests fail closed; update SDK and API together. Existing receipts remain readable, but replaying a pre-change request ID with a new fingerprint requires a new invocation ID. Authorization and receipt/quota reservation precede command dispatch. Dispatch has a bounded timeout using the signed action timeout_ms; failure rolls back the receipt. Successful read retries may still return current read data rather than a historical snapshot; receipt quota measures new successful invocations, not every failed request or retry. Catalog admission occurs before opening the scoped database transaction to avoid nested pool acquisition.
GET /organizations/{organization_id}/projects/{project_id}/extensions/v2-audit exposes only the authenticated human actor's own project receipts (1–100 rows, UUID cursor); input/output bodies are never returned. Available even when runtime is disabled. Web host exports the visible page as JSON. This is not a complete organization audit, archival snapshot, or permission to delete a project with retained evidence.
