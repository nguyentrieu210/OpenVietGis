# Mobile human authentication v2 — additive proposal
Owner E10 plus existing identity/route owners. Baseline extensions/mod.rs treats Bearer as service credential; human cookie/session/CSRF remains unchanged. Inventory all route families (identity, catalog, edits, tiles, field/managed sync, plugins, jobs, media, events). No generic bearer-to-human fallback or token reuse across servers.
## Proposed flow
Trusted HTTPS server identified by canonical origin + server instance/issuer ID, discovery verified against chosen origin; self-host user confirmation, no redirects to untrusted issuer. System browser authorization code with PKCE S256, cryptographically random state and OIDC nonce, registered exact app/universal redirect, one-time code with expiry and binding to public client/redirect/verifier. No embedded login form or client secret. Validate issuer/audience, nonce/state and signature as applicable. Prefer platform existing identity provider, additive mobile authorization exchange only after actual inventory. 
Server issues dedicated human mobile session with typed credential namespace, short-lived opaque access token (proposal 10 min) and rotating opaque refresh token (proposal 30 days idle, 90 days absolute; final security review). Store token hashes server side, session/device ID, subject, audience, scopes, expiry, revocation and token family. Access tokens resolve to same human tenant/permission policy as web; no trust in app claims; every route checks current grants and project scope. Service credentials remain service-only. Reject credential-type confusion and wrong issuer/audience; no weakening cookie CSRF checks. 
Refresh is single-flight per session; rotate atomically and detect reuse, revoke affected family, no retry with stale refresh after uncertain success (reauthenticate or use reviewed replay-safe protocol). Logout/revoke invalidate session and stop streams, managed cache locks according to offline contract. Secure storage OS keystore/keychain; no tokens in URLs, logs, crash dumps, plugins or exports. Offline lease is distinct, never online bearer.
## Gate
Before T043 connected implementation, freeze actual route/auth mapping with versioned OpenAPI and threat model; negative tests for wrong redirect/verifier/nonce, replay, expired/revoked tokens, service vs human confusion, cross-origin and cross-tenant, refresh race, stream revocation and Web session/CSRF regression. Token durations above proposed limits to validate, not implemented APIs.

## Isolated HTTP candidate
Non-default Rust feature `mobile-auth-candidate` mounts POST `/api/v1/mobile/auth/grant`, `exchange`, `refresh`, `revoke` and GET `session`. Uses reviewed HTTPS origin derived from server configuration and exact `/mobile/callback`, fixed public client ID `openvietgis-mobile`. Grant requires existing human cookie, CSRF and explicit consent; returns short-lived code as no-store JSON. Native token endpoints reject cookies and browser Origin, and never accept service credentials. Token response includes issuer, subject, device and session IDs; no project authorization is implied. This is an isolated contract candidate only: browser consent UI, mobile state/nonce and app-link qualification, rate limits, migration/RLS review, secure key storage and per-route permission integration remain release blockers. Do not enable in production.
